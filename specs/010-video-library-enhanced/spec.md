# Feature Specification: 视频库增强

**Feature Branch**: `010-video-library-enhanced`
**Created**: 2026-05-31
**Status**: Draft
**Input**: From PRD v1.0 for yt-dlp subscription manager desktop app (P1 Enhancement Phase)

## User Scenarios & Testing *(mandatory)*

### 用户故事 1：高级搜索（多条件）（优先级：P1）

作为拥有大量下载视频的用户，我希望通过多个条件组合搜索已下载的视频，以便快速找到目标视频。

**Why this priority**: 当下载记录量积累到 100+ 时，基本标题搜索已不够用，多条件搜索是日常高频需求。

**Independent Test**: 创建 20 条不同状态、不同频道、不同日期的下载记录，使用多条件搜索验证结果准确。

**Acceptance Scenarios**:

1. **Given** 用户有来自 YouTube 和 Bilibili 的下载记录，**When** 用户搜索"python tutorial"并设置平台筛选为 YouTube，**Then** 结果仅显示标题包含"python tutorial"的 YouTube 视频。

2. **Given** 用户想要查找下载失败的视频，**When** 用户筛选状态为"失败"，**Then** 结果仅显示下载失败的记录。

3. **Given** 用户想查找最近一周下载的视频，**When** 用户设置日期范围为"最近 7 天"，**Then** 结果仅显示过去 7 天内下载的视频。

4. **Given** 用户设置多个筛选条件（状态"已完成" + 日期"本月" + 搜索关键字"入门"），**When** 滤镜应用，**Then** 结果同时满足所有条件。

5. **Given** 用户清空所有筛选条件，**When** 点击重置，**Then** 显示全部下载记录。

**Edge Cases**:
- 搜索结果为空时显示空状态提示和"清除筛选"按钮
- 搜索关键字包含正则特殊字符时按字面匹配
- 日期范围"今天"需精确到当日 00:00 开始
- 搜索结果数量 > 1000 时分页显示

### 用户故事 2：视频信息提取（优先级：P2）

作为用户，我希望查看每个已下载视频的详细信息（时长、分辨率、编解码器、文件大小等），以便更好地管理视频库。

**Why this priority**: 视频元数据增强管理能力，但不是下载流程的必要部分。

**Independent Test**: 下载一个视频，在记录详情中查看时长、分辨率、文件大小等信息，验证与实际文件一致。

**Acceptance Scenarios**:

1. **Given** 用户点击一条下载记录，**When** 详情面板展开，**Then** 显示视频时长、分辨率、文件大小、格式（编解码器）、下载日期、来源订阅。

2. **Given** 系统使用 yt-dlp 下载时，**When** 下载完成，**Then** 同时提取并通过 `--print` 获取文件大小、时长等元数据，存入下载记录。

3. **Given** 用户在资源管理器中删除了视频文件，**When** 系统检测到文件缺失，**Then** 仅显示存储的元数据，并标注"文件缺失"。

4. **Given** 视频元数据包含缩略图 URL，**When** 详情面板加载，**Then** 显示缩略图（异步加载，不阻塞面板渲染）。

**Edge Cases**:
- 部分元数据获取失败时（如 yt-dlp 不提供某字段），显示"未知"
- 文件大小格式化为人类可读格式（MB、GB）
- 时长格式化为 `HH:MM:SS` 格式

### 用户故事 3：批量删除操作（优先级：P2）

作为用户，我希望能一次性删除多个下载记录及其对应文件，以便清理不需要的视频。

**Why this priority**: 批量操作提升效率，但单条删除已能满足基本需求。

**Independent Test**: 选择 5 条下载记录，执行批量删除，验证记录和对应文件都被删除。

**Acceptance Scenarios**:

1. **Given** 用户通过复选框选择了 3 条下载记录，**When** 用户点击"删除选中"，**Then** 弹出确认对话框显示影响数量，确认后删除所有对应文件和记录。

2. **Given** 用户选择"删除所有失败记录"，**When** 用户确认操作，**Then** 所有失败状态的下载记录被删除。

3. **Given** 用户批量删除 50 条记录，**When** 执行删除，**Then** 显示进度（已删除 N/50），操作可取消。

4. **Given** 部分文件已被手动删除（记录仍在），**When** 执行批量删除，**Then** 仅删除记录，文件删除失败跳过错不中断整体流程。

**Edge Cases**:
- 批量删除前必须显示确认对话框，防止误操作
- 删除操作应异步执行，不阻塞 UI
- 删除文件失败不影响记录删除（文件已不存在）
- 无选中项时"删除选中"按钮禁用

### 用户故事 4：视频分类筛选（优先级：P2）

作为用户，我希望按平台、订阅、日期等维度筛选和分组视频，便于按类别浏览。

**Why this priority**: 分类筛选提升浏览效率，对拥有多类型视频库的用户价值更高。

**Independent Test**: 从 YouTube 和 Bilibili 各下载 5 个视频，按平台筛选，验证结果正确分组。

**Acceptance Scenarios**:

1. **Given** 用户有多个订阅的视频，**When** 用户按来源订阅筛选，**Then** 结果仅显示来自该订阅的视频。

2. **Given** 用户想按月份查看下载记录，**When** 用户选择日期分组为"按月"，**Then** 视频按月份分组显示（如"2026 年 5 月"）。

3. **Given** 用户想查看文件大小最大的视频，**When** 用户按文件大小降序排列，**Then** 视频按文件大小从大到小显示。

4. **Given** 用户按画质筛选，**When** 选择"1080p"，**Then** 显示所有 1080p 视频。

**Edge Cases**:
- 分组模式下删除组内全部视频后，分组自动消失
- 无画质信息的旧记录在画质筛选中归入"未知"分组
- 日期分组跨年时正确显示年份

### 用户故事 5：播放计数记录（优先级：P3）

作为用户，我希望系统记录每个视频的播放次数，以便了解哪些视频最常观看。

**Why this priority**: 播放计数是增值功能，不影响核心下载管理流程。

**Independent Test**: 点击打开一个视频 3 次，查看记录中的播放次数是否为 3。

**Acceptance Scenarios**:

1. **Given** 用户通过"打开文件"按钮打开了一个视频，**When** 系统检测到打开操作，**Then** 播放计数 +1。

2. **Given** 视频的播放计数为 5，**When** 用户查看下载记录列表，**Then** 播放次数显示在记录行中。

3. **Given** 用户想按播放次数排序，**When** 选择排序方式为"播放次数"降序，**Then** 按播放次数排列。

4. **Given** 用户右键点击视频记录，**When** 选择"重置播放计数"，**Then** 该视频的播放计数归零。

**Edge Cases**:
- 频繁打开同一视频（如测试），播放计数正常递增
- 播放计数超过 999 时显示为 "999+"
- 删除视频记录时同时清除播放计数

## Requirements *(mandatory)*

### Functional Requirements

**高级搜索**:
- FR-001: 系统必须提供关键字搜索，在标题、频道名中匹配
- FR-002: 系统必须提供平台筛选（YouTube / Bilibili / 其他）
- FR-003: 系统必须提供下载状态筛选（已完成、进行中、失败、跳过）
- FR-004: 系统必须提供日期范围筛选（今天、7 天、30 天、自定义范围）
- FR-005: 多条件必须使用 AND 逻辑组合
- FR-006: 系统必须提供"重置筛选"按钮一键清除所有条件

**视频信息提取**:
- FR-007: 系统必须在下载完成后提取视频元数据（时长、分辨率、文件大小、编解码器）
- FR-008: 元数据必须持久化到下载记录中
- FR-009: 元数据缺失时显示"未知"而非空字符串

**批量删除操作**:
- FR-010: 系统必须支持多选（复选框）并批量删除
- FR-011: 系统必须提供快捷批量操作："删除全部失败""删除选中"
- FR-012: 批量删除必须异步执行并显示进度
- FR-013: 文件删除失败不得影响记录删除

**视频分类筛选**:
- FR-014: 系统必须支持按来源订阅筛选
- FR-015: 系统必须支持按画质筛选
- FR-016: 系统必须支持按日期分组显示（按月）
- FR-017: 排序维度必须包括：下载日期、文件大小、播放次数

**播放计数**:
- FR-018: 系统必须在用户打开视频文件时自动增加播放计数
- FR-019: 播放计数必须持久化到下载记录中
- FR-020: 系统必须提供重置播放计数的功能

### Key Entities

- **DownloadRecord 扩展字段**: `{ duration: number | null, resolution: string | null, codec: string | null, file_size: number | null, play_count: number }`
- **SearchFilter**: `{ keyword: string, platform: string | null, status: string | null, date_from: string | null, date_to: string | null }`
- **GroupByMode**: `"none" | "month" | "subscription" | "platform"`

## Success Criteria *(mandatory)*

### Measurable Outcomes

- SC-001: 高级搜索响应时间 < 200ms（1000 条记录内，本地过滤）
- SC-002: 批量删除 100 条记录在 10 秒内完成
- SC-003: 视频元数据提取成功率 > 95%
- SC-004: 播放计数更新不影响页面响应（< 50ms）
- SC-005: 搜索高亮匹配文本无明显性能影响

## Assumptions

1. 下载记录本地过滤完全在前端执行，无需后端查询（记录量级 < 10000）
2. 视频元数据通过 yt-dlp 的 `--print after_move:filename` + 文件系统 `stat` 获取
3. 播放计数基于用户在应用内"打开文件"操作，而非系统级文件访问监控
4. 下载记录结构需扩展以支持新增字段（duration、resolution、codec、file_size、play_count）
5. 批量删除的最大选中数不超过 200 条（超出分页限制）
6. 日期分组使用下载记录的 completed_at 时间戳
