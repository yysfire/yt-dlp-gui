# Feature Specification: 核心下载功能

**Feature Branch**: `001-mvp-core-features`

**Created**: 2026-05-31

**Status**: Draft

**Input**: 来自 PRD v1.0，yt-dlp 桌面端订阅管理器

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自动定时检查更新 (Priority: P1)

系统按照用户设定的时间间隔（如每小时、每天），在后台自动检查所有已启用订阅是否有新视频。检查完成后，新发现的视频自动加入下载队列，无需用户手动干预。

**Why this priority**: 自动检查是应用的核心价值——让用户无需手动关注频道更新即可自动获取新内容。

**Independent Test**: 设置较短的检查间隔（如 5 分钟），向某频道添加新视频后等待检查触发，验证新视频是否被检测到并加入下载队列。

**Acceptance Scenarios**:

1. **Given** 用户已启用定时检查并设置了检查频率为每小时，**When** 自上次检查起满一小时，**Then** 系统自动启动一轮检查，对所有已启用订阅进行检查。
2. **Given** 某频道有新视频发布，**When** 定时检查执行到该频道，**Then** 系统检测到新视频，将其加入下载队列，并在界面上更新该订阅的状态。
3. **Given** 用户退出了应用，**When** 应用重新启动，**Then** 定时检查器自动恢复运行，按剩余时间计算下次检查时间。
4. **Given** 所有已启用订阅的检查均已完成，**When** 未发现任何新视频，**Then** 系统安静完成本轮检查，不产生任何下载任务。

---

### User Story 2 - 基本下载队列（FIFO）(Priority: P1)

当检测到新视频后，下载任务按先进先出的顺序排队执行。用户可以查看队列中等待、进行中和已完成的下载任务。

**Why this priority**: 有序的下载管理是核心下载体验的基础，防止多个下载任务无序抢占资源。

**Independent Test**: 触发多个视频的下载，观察队列是否按检测顺序依次进行下载。

**Acceptance Scenarios**:

1. **Given** 系统检测到频道 A 有 3 个新视频，频道 B 有 2 个新视频，**When** 自动检查完成，**Then** 下载队列中包含 5 个任务，按检测时间顺序排列。
2. **Given** 下载队列中有一个任务正在进行，**When** 该任务完成，**Then** 系统自动开始下一个等待中的任务。
3. **Given** 下载队列为空，**When** 新任务加入队列，**Then** 系统立即开始下载该任务。
4. **Given** 同时有多个下载任务完成，**When** 用户查看下载记录，**Then** 所有任务状态正确更新为"已完成"。

---

### User Story 3 - 下载进度显示 (Priority: P2)

用户可以在下载管理页面实时查看每个下载任务的进度，包括已下载百分比、下载速度、预估剩余时间等信息。

**Why this priority**: 进度显示让用户了解下载状态，减少等待焦虑，提升使用信心。

**Independent Test**: 启动一个大文件的下载，观察进度条和速度信息是否实时更新。

**Acceptance Scenarios**:

1. **Given** 一个下载任务正在进行，**When** 用户查看下载管理页面，**Then** 该任务显示进度百分比、当前下载速度和已下载/总大小。
2. **Given** 下载任务进度为 50%，**When** 再过几秒后刷新，**Then** 进度数字上升，反映最新状态。
3. **Given** 某个下载任务的视频文件较小（下载很快完成），**When** 下载完成，**Then** 进度跳至 100%，任务状态变为"已完成"。

---

### User Story 4 - 暂停/继续/取消单个下载 (Priority: P2)

用户可以对单个下载任务进行控制：暂停正在下载的任务、继续已暂停的任务、取消不再需要的下载。

**Why this priority**: 让用户在遇到网络波动或改变主意时能灵活控制下载行为。

**Independent Test**: 在下载过程中点击暂停，再点击继续，最后点击取消，验证每个操作都正确响应。

**Acceptance Scenarios**:

1. **Given** 某个下载任务正在下载中，**When** 用户点击"暂停"，**Then** 该任务状态变为"已暂停"，下载停止，已下载部分保留。
2. **Given** 某个下载任务处于"已暂停"状态，**When** 用户点击"继续"，**Then** 该任务恢复下载，从断点继续。
3. **Given** 某个下载任务正在进行或已暂停，**When** 用户点击"取消"，**Then** 该任务状态变为"已取消"，已下载的部分文件被清理。
4. **Given** 用户取消了队列中的某个任务，**When** 队列中该任务之后的任务，**Then** 自动继续排队，不受影响。

---

### User Story 5 - 重复下载避免（基于视频ID）(Priority: P1)

系统基于视频的唯一 ID 判断是否已下载过，避免重复下载相同视频。即使同一视频出现在不同播放列表中，也仅下载一次。

**Why this priority**: 重复下载浪费带宽和存储空间，是用户体验的基本保障。

**Independent Test**: 手动触发两次对同一频道的检查，验证已下载的视频不会再次进入下载队列。

**Acceptance Scenarios**:

1. **Given** 视频 A 已被下载过且文件仍在，**When** 系统再次检测到视频 A，**Then** 该视频不会被加入下载队列。
2. **Given** 视频 B 之前因失败未完整下载，**When** 系统再次检测到视频 B，**Then** 该视频可被重新加入下载队列（失败记录允许重试）。
3. **Given** 视频 C 已下载但用户手动删除了文件，**When** 系统再次检测到视频 C，**Then** 系统根据下载记录判断已下载，不重复下载（除非用户主动请求重新下载）。
4. **Given** 同一视频同时存在于两个订阅频道的播放列表中，**When** 系统分别检查这两个频道，**Then** 视频仅被加入下载队列一次。

---

### Edge Cases

- 定时检查期间应用被关闭（系统关机、崩溃），再次启动时如何处理未完成的检查？
- 下载过程中网络中断，如何处理？超时重试几次？
- 下载的文件已存在同名文件时如何处理？
- 磁盘空间不足时，下载任务如何响应？
- 同时有大量（50+）新视频需要下载时，内存和系统资源是否足够？
- yt-dlp 进程崩溃或返回非预期输出时，下载任务如何标记和恢复？
- 暂停后继续下载但原临时文件已被意外删除，如何处理？
- 视频 ID 相同但画质设置不同的情况如何判断"重复"？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持按设定的时间间隔自动检查所有已启用订阅的新视频。
- **FR-002**: 系统必须将检测到的新视频按 FIFO 顺序加入下载队列。
- **FR-003**: 系统必须在下载过程中实时显示进度（百分比、速度、大小）。
- **FR-004**: 系统必须支持暂停正在进行的下载任务。
- **FR-005**: 系统必须支持继续已暂停的下载任务。
- **FR-006**: 系统必须支持取消下载任务（包括等待中和进行中的任务）。
- **FR-007**: 系统必须基于视频唯一 ID 判断重复，避免重复下载。
- **FR-008**: 系统必须在下载完成后持久化记录下载状态。
- **FR-009**: 系统必须支持并发下载任务数可配置。
- **FR-010**: 系统必须在下载失败时记录失败原因，允许后续重试。
- **FR-011**: 取消下载任务时，系统必须清理已下载的部分文件。
- **FR-012**: 应用重启后，定时检查器必须恢复运行。

### Key Entities

- **DownloadTask**: 下载任务实体，包含视频 ID、视频标题、所属订阅 ID、下载状态（等待中/进行中/已暂停/已完成/已失败/已取消）、进度百分比、文件大小、下载速度、创建时间、完成时间、失败原因。
- **DownloadRecord**: 下载记录实体，持久化存储已完成/失败的下载信息，用于避免重复下载。包含视频 ID、标题、下载状态、文件路径、下载时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 定时检查触发的时间误差不超过检查间隔的 10%。
- **SC-002**: 下载队列在包含 50 个任务时，任务切换延迟不超过 2 秒。
- **SC-003**: 重复下载误判率低于 1%（基于视频 ID 匹配）。
- **SC-004**: 暂停/继续操作的响应时间不超过 1 秒。
- **SC-005**: 取消下载操作的响应时间不超过 3 秒（含文件清理）。
- **SC-006**: 应用重启后，未完成的下载任务状态和定时检查器状态正确恢复。

## Assumptions

- 用户设备已安装 yt-dlp 命令行工具，支持断点续传功能。
- yt-dlp 的 `--flat-playlist` 输出包含视频 ID 字段用于去重判断。
- 默认并发下载数为 1，用户可在设置中调整。
- 下载失败后默认不自动重试，用户可通过手动检查触发重试。
- 暂停功能依赖 yt-dlp 的进程控制（SIGSTOP/SIGCONT），而非 yt-dlp 原生的暂停 API。
