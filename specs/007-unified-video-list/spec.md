## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看订阅的完整视频状态（P1）

用户在订阅详情页能看到一个统一的视频列表，每个视频一目了然地展示其状态：未下载、等待下载、正在下载、已完成或失败。不再需要上下滚动对比两个分离的列表区域。

**Why this priority**: 这是核心体验改进——解决当前"频道视频"和"下载记录"两个独立区域导致的视觉重复和信息割裂问题。没有这个基础合并，其他功能（后台加载、过滤）都没有意义。

**Independent Test**: 选中任意有下载记录的订阅，右侧详情面板渲染单一视频列表。列表中的视频按状态分区显示，每个视频条目同时包含频道元信息（标题、日期、时长）和下载状态（已完成/下载中/失败）。

**Acceptance Scenarios**:

1. **Given** 某订阅有 3 条已完成下载记录和 5 个未下载新视频，**When** 用户点击该订阅，**Then** 右侧面板显示一个包含 8 个条目的统一列表，无重复视频
2. **Given** 某视频既在频道播放列表中又已被下载，**When** 渲染统一列表，**Then** 该视频仅出现一次，显示"已完成"状态及文件大小、下载时间
3. **Given** 用户切换订阅，**When** 新订阅加载完成，**Then** 列表清空旧内容并显示新订阅的视频，无残留数据

---

### User Story 2 - 后台自动加载全部频道视频（P2）

用户打开订阅详情后，系统自动在后台逐页拉取该频道的所有视频，用户无需点击"加载更多"按钮，视频列表自动增长直到全部加载完成。

**Why this priority**: 消除手动翻页操作，让用户感知到"订阅的全部视频一览无余"。依赖 P1 的统一列表基础。

**Independent Test**: 选中一个有 50+ 个视频的频道，列表先显示第 1 页（10 条）+ 下载记录，随后自动追加后续页面视频，无需用户操作。

**Acceptance Scenarios**:

1. **Given** 频道有 50 个视频，**When** 用户打开该订阅，**Then** 首屏显示第 1 页视频 + 已有下载记录，后台自动加载第 2~5 页并静默追加
2. **Given** 后台加载中途用户切换到另一个订阅，**When** 切换发生，**Then** 上一个订阅的后台加载被取消，新订阅开始自己的加载
3. **Given** 后台加载第 N 页时网络出错，**When** 错误发生，**Then** 已加载的视频保留在列表中，不再继续加载，无崩溃

---

### User Story 3 - 下载中视频实时展示进度（P3）

当某个视频正在下载时，其在统一列表中的对应条目实时更新进度条和下载百分比，用户无需切换到其他界面即可观察下载进度。

**Why this priority**: 增强下载过程的透明度和即时反馈。依赖 P1 的统一列表包含下载状态。

**Independent Test**: 触发一个下载任务，观察详情面板中该视频条目的进度条从 0% 逐步增长到 100%，完成后状态变为"已完成"。

**Acceptance Scenarios**:

1. **Given** 某视频处于下载队列中，**When** 下载开始，**Then** 列表顶部出现该视频条目，状态为"下载中"，显示进度条和百分比
2. **Given** 某视频正在下载，**When** 下载完成，**Then** 条目状态变为"已完成"，进度条消失，显示文件大小和下载时间
3. **Given** 某视频下载失败，**When** 错误发生，**Then** 条目状态变为"失败"，显示错误信息，右侧出现"重试"按钮

---

### Edge Cases

- 频道已失效（死链）时，列表不加载频道视频，仅显示已有下载记录
- 频道视频列表为空但存在下载记录时（仅下载了旧视频），列表只展示下载记录
- 同一视频多次下载（重试/重新下载）时，以最新状态为准，不出现重复条目
- 用户快速切换订阅时，确保不存在竞态条件导致旧订阅数据覆盖新订阅
- 频道有上千个视频时，后台分页加载不会阻塞 UI 响应
- 下载记录的 `video_id` 为空时，回退使用 `video_url` 进行合并匹配

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 订阅详情面板 MUST 展示单一合并视频列表，而非两个独立区域（"频道视频"和"下载记录"）
- **FR-002**: 系统 MUST 按 `video_id`（优先）和 `video_url`（回退）将频道视频与下载记录合并为统一条目
- **FR-003**: 统一列表中每个视频条目 MUST 以三行三列网格布局展示左侧状态图标（垂直居中），中间标题+元信息+进度条，右侧操作按钮（垂直居中）
- **FR-004**: 列表 MUST 按以下优先级排序：下载中/等待中 → 已暂停 → 已完成（按下载时间倒序） → 未下载（按上传日期倒序） → 仅下载记录的旧视频（按下载时间倒序） → 失败
- **FR-005**: 打开订阅详情时，系统 MUST 先展示已有下载记录，再异步加载频道视频第 1 页并合并
- **FR-006**: 第 1 页加载完成后，系统 MUST 在后台自动逐页加载剩余频道视频并静默追加，无需用户手动触发
- **FR-007**: 切换订阅时，系统 MUST 取消进行中的后台加载并清空旧列表
- **FR-008**: 下载中的视频条目 MUST 实时展示进度条和百分比，进度条占满条目的中间列宽度
- **FR-009**: 下载完成、失败、新下载开始时，对应条目 MUST 自动更新状态而无需手动刷新
- **FR-010**: 旧下载记录中不在频道视频列表内的视频 MUST 保留在统一列表中，仅缺少频道元信息
- **FR-011**: 频道已失效时，列表 MUST 仅展示已有下载记录，不尝试加载频道视频
- **FR-012**: `DownloadRecordList` 组件 MUST 被移除，其职责由 DetailPanel 内部合并逻辑接管
- **FR-013**: 全局"已下载"视图（`DownloadedList`）MUST 保持不变，不受 DetailPanel 重构影响

### Key Entities

- **UnifiedVideoItem**: 统一视频条目，关联可选的频道视频信息（`channelInfo`）和可选的下载记录（`downloadInfo`/`queueTask`），派生统一的 id、title、url、status 字段
- **VideoStatus**: 视频在统一列表中的展示状态——`new`（未下载）、`waiting`（等待中）、`downloading`（下载中）、`paused`（已暂停）、`completed`（已完成）、`failed`（失败）、`cancelled`（已取消）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户打开任意订阅详情后，1 秒内看到已有下载记录，3 秒内看到合并后的统一列表
- **SC-002**: 同一视频在详情面板中仅出现一次（无论是否已下载），消除当前 100% 的重复展示问题
- **SC-003**: 后台自动加载过程中，UI 无卡顿或闪烁，用户可随时切换订阅或滚动列表
- **SC-004**: 下载中视频的进度条更新延迟不超过 1 秒
- **SC-005**: 有 100+ 个视频的频道，后台加载全部视频的过程不影响前端操作流畅性

## Assumptions

- yt-dlp 的 `--flat-playlist` 输出中 `id` 字段（平台视频 ID）存在且与 `DownloadRecord.video_id` 一致
- 后台分页采用每页 10 条的容量，与当前 `getChannelVideos` 分页参数保持一致
- 下载进度更新通过现有的 Tauri 事件系统（`records-changed`、`queue-changed`）推送，前端监听后更新对应条目
- 用户的目标平台支持 `requestIdRef` 竞态取消模式（React useRef-based），用于切换订阅时取消进行中的请求
- `DownloadProgressBar` 组件保持可用，不被移除，在统一列表的下载中条目中复用
- 全局"已下载"视图（`DownloadedList`）和其子组件（`DownloadedItem`）不在此功能范围内修改
