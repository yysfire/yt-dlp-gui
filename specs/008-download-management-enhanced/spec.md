## User Scenarios & Testing *(mandatory)*

### 用户故事 1：智能重复检测增强（优先级：P1）

作为用户，我希望系统在下载前能更智能地判断视频是否已下载过，不仅基于视频 ID，还要考虑**画质变化**，避免重复下载但不错过画质升级。

> 「格式变化」不在本次范围（属故事 5）—— 见「范围界定」。

**Why this priority**: 重复下载不仅浪费带宽，还浪费存储空间，增强检测直接影响核心下载效率。

**Independent Test**: 先以 **720p** 下载某视频，再把该订阅的画质设为 **1080p** 并重新检查该频道 —— 验证列表把这一行标为「可升级 1080p」，点击「升级」后该视频被重下为 1080p、记录更新为 1080p，且**只有一份文件**。

**Acceptance Scenarios**:

1. **Given** 用户已下载视频 A（720p），**When** 系统检查到视频 A 且**画质档次与已下载相同**，**Then** 系统自动跳过，不重复下载。

2. **Given** 用户已下载视频 B（720p），**When** 用户把该订阅的画质设置为 1080p 并重新检查同一频道，**Then** 列表把视频 B 标为「可升级 1080p」；**用户点击「升级」后**系统以下载记录为准重下该视频（覆盖同一路径），记录画质更新为 1080p。**系统不自动下载**。

3. **Given** 用户已下载视频 C（1080p），**When** 用户把该订阅的画质设置为 720p（**降级**），**Then** 系统**不提示**任何升级或变化。

4. **Given** 一条旧记录（本次改动之前写入，没有画质字段），**When** 用户检查该频道，**Then** 系统**不判定**它可升级（画质未知时永不提示，宁可漏报）。

5. **Given** 两个不同频道发布了标题完全相同的视频，**When** 系统检查重复，**Then** 基于**视频 ID** 判断为不同视频，不误判重复。

6. **Given** 用户手动删除了本地文件但记录仍存在，**When** 周期文件同步检测到文件不在磁盘上，**Then** 列表把该行**呈现**为「文件缺失」，用户可点击「重新下载」；**系统不自动重新下载**。

7. **Given** 同一视频已被订阅 A 下载，**When** 用户查看订阅 B 的列表（B 的频道里也有该视频），**Then** 该行显示为「**已在其它订阅下载**」，**不**显示为「新视频」，也**不**提供重下或升级。

**画质升级判定规则**（可直接翻译成测试用例）：

- 画质档次全序：`480p < 720p < 1080p < 1440p < 2160p < best`。
- **未知值永不参与比较**：记录侧画质为空（旧记录）→ 不提示；订阅侧画质未知 → 不提示。
- 仅当**订阅当前画质档次高于**记录中记录的下档次时提示可升级；**同档与降级都不提示**。
- 判定**只看本订阅的记录**；其它订阅的记录用「已在其它订阅下载」呈现（场景 7）。
- 「文件缺失」**优先于**「可升级」：文件缺失时不显示升级，动作是「重新下载」。

**Edge Cases**:

- 视频 ID 相同的播放列表项应视为同一视频。
- **用户更改下载路径后**：**不处理**。旧记录的 `file_path` 是绝对路径，改目录后会被显示为「文件缺失」，需**手动**重新下载。（自动重下会导致「改一次目录 → 全库重下」。）
- 文件名模板变化导致同名文件但视频 ID 不同时，不应判定为重复（去重基于视频 ID，天然满足）。
- 文件系统大小写不敏感（macOS / Windows）不应导致误判（去重基于视频 ID，天然满足）。

### 用户故事 2：失败自动重试（优先级：P1）

作为用户，我希望下载失败时系统能自动重试，而不是立即放弃，以便在网络波动或临时错误时自动恢复下载。

**Why this priority**: 网络临时波动是最常见的下载失败原因，自动重试可以显著减少用户手动干预，提升下载成功率。

**Independent Test**: 让一条下载遇到可重试的失败（例如抓取阶段返回 HTTP 503），验证系统在 30 秒后自动重试、最终成功；记录终态为 `completed` 且 `retry_count` 反映实际重试次数。

**Acceptance Scenarios**:

1. **Given** 一个下载任务因网络超时失败，**When** 失败发生，**Then** 系统自动在 30 秒后重试，最多重试 3 次，每次重试间隔递增（30s、60s、120s）。

2. **Given** 一个下载任务在第 2 次重试时成功，**When** 下载完成，**Then** 记录状态更新为 `completed`，`retry_count` **保留为 2**（成功不归零）。

3. **Given** 一个下载任务重试 3 次全部失败，**When** 达到最大重试次数，**Then** 记录标记为 `failed`，`error_message` 为**真实失败原因**，用户可手动重新下载。

4. **Given** 多个下载任务同时失败，**When** 系统对它们分别重试，**Then** 各任务独立重试计数，互不影响。

5. **Given** 一条下载在退避等待期间，**When** 用户查看列表，**Then** 该行显示为「**重试中 (n/3)**」并**带下一次重试的倒计时**。

**重试判定规则**（可直接翻译成测试用例）：

判定**只针对 stderr 中最后一条 `ERROR:` 行**（`WARNING:` 行里会合法出现 `HTTP Error 403` 这类假阳性文本，不能参与判定）。按以下顺序：

1. **退出码**：拿不到退出码（`spawn` 失败或被信号终止）、`2`（参数错误）、`101`（取消）→ **不重试**。
2. **终态黑名单** → 不重试：`Requested format is not available`、`Unsupported URL`、DRM、需登录、私享 / 已删除 / 不可用、`Sign in to confirm`、地区限制。
3. **HTTP 状态白名单** → 仅 `5xx`、`408`、`429` 重试；其余 4xx 不重试。代理 407 表现为 `Tunnel connection failed: 407`，需单独识别。
4. **网络白名单** → 重试：连接失败 / DNS 解析失败 / 超时 / 连接重置 / TLS 失败 / 代理握手失败等。
5. **其余一律视为可重试**（宁可多试，不可漏试）。

**Edge Cases**:

- HTTP **5xx、408、429** 与**网络类错误**（超时 / DNS / TLS / 代理握手）应重试。
- 其余 **4xx**（如 401、403、404、410）**不得**重试。
- **无状态码的终态失败**（格式不可用、私享 / 已删除、需登录、URL 不合法）**不得**重试。
- 下载被用户**手动取消**后不自动重试；取消会**立即中断**正在等待的退避。
- **暂停任务**会冻结退避计时；**恢复**后从剩余时间继续。
- **暂停订阅不中断**已入队下载的重试（暂停只让「检查」跳过该订阅）。
- **退避等待期间仍占用并发名额**（不释放给其它任务）。
- **`yt-dlp` 可执行文件起不来**（路径不存在 / 无执行权限）属配置问题，**不重试**。
- 用户手动触发的「重新下载」**不受**自动重试策略影响。

### 用户故事 3：下载速度限制（优先级：P2）

> ⚠️ **本次范围外** —— 与 P1 无共享决策，留待独立推进。以下为原始描述，**未按本次决策修订**。

作为用户，我希望限制下载速度，以便在使用网络的同时不影响其他网络活动（如在线会议、流媒体）。

**Why this priority**: 下载抢占带宽是常见痛点，但用户可以在下载时手动暂停，因此优先级略低。

**Independent Test**: 设置下载限速为 1MB/s，启动下载并监控实际网络速度，验证下载速度不超过设定值。

**Acceptance Scenarios**:

1. **Given** 用户在设置中将下载限速设为 2MB/s，**When** 下载开始，**Then** yt-dlp 以 `--limit-rate 2M` 参数调用，下载速度不超过 2MB/s。

2. **Given** 用户设置下载限速为"无限制"，**When** 下载开始，**Then** yt-dlp 不传递 `--limit-rate` 参数，以最大可用带宽下载。

3. **Given** 下载正在进行中，**When** 用户动态调整限速值，**Then** 新限速对后续下载任务生效，当前进行中的任务不变。

4. **Given** 用户设置限速后没有网络活动，**When** 下载速度低于限速值，**Then** 以实际可用带宽下载。

**Edge Cases**:

- 限速值设为 0 或负数时，视为"无限制"
- 限速值超过物理带宽时以实际带宽为准
- 限速单位转换清晰（KB/s vs Kbps），前端统一使用 KB/s

### 用户故事 4：网络代理支持（优先级：P2）

> ⚠️ **本次范围外** —— 代理主体（`--proxy` 透传 + `validate_proxy_url` 命令）**已实现**；剩下的「认证 + 测试连接」留待独立推进。以下为原始描述，**未按本次决策修订**。

作为需要通过代理访问网络的用户，我希望为下载配置 HTTP/HTTPS/SOCKS 代理，以便在受限网络环境中正常下载。

**Why this priority**: 中国大陆等地区访问 YouTube 需要代理，但代理配置是一次性操作，优先级略低于核心功能。

**Independent Test**: 配置一个 SOCKS5 代理，下载一个视频，验证 yt-dlp 使用代理参数并成功下载。

**Acceptance Scenarios**:

1. **Given** 用户在设置中配置了 SOCKS5 代理 `127.0.0.1:1080`，**When** 下载开始，**Then** yt-dlp 以 `--proxy socks5://127.0.0.1:1080/` 参数调用。

2. **Given** 用户配置了 HTTP 代理 `https://proxy.example.com:8080`，**When** 下载开始，**Then** yt-dlp 以 `--proxy https://proxy.example.com:8080/` 参数调用。

3. **Given** 用户未配置代理，**When** 下载开始，**Then** yt-dlp 不传递 `--proxy` 参数，使用直连。

4. **Given** 代理需要认证，**When** 用户配置了用户名和密码，**Then** yt-dlp 正确使用带认证的代理 URL（如 `socks5://user:pass@127.0.0.1:1080/`）。

5. **Given** 代理连接失败，**When** 下载失败，**Then** 错误信息明确提示"代理连接失败"，而非通用网络错误。

**Edge Cases**:

- 代理 URL 格式无效时，保存前进行格式校验
- 代理密码包含特殊字符时进行 URL 编码
- 仅填写主机名未填端口时使用默认端口（HTTP 80、SOCKS5 1080）
- 代理配置变更后立即对所有后续下载生效

### 用户故事 5：音频下载支持（优先级：P2）

> ⚠️ **本次范围外** —— 独立特性，留待独立推进。以下为原始描述，**未按本次决策修订**。

作为用户，我希望在视频下载之外支持仅下载音频，以便节省存储空间和带宽。

**Why this priority**: 音频下载是许多用户的需求，但核心功能是视频下载，音频模式作为扩展功能。

**Independent Test**: 设置下载模式为"仅音频"，下载一个视频，验证仅下载音频，文件大小为纯音频大小。

**Acceptance Scenarios**:

1. **Given** 用户在设置中选择"仅音频"模式并指定格式为 m4a，**When** 下载开始，**Then** yt-dlp 以 `-f bestaudio[ext=m4a]` 参数调用。

2. **Given** 用户选择"仅音频"模式，**When** 视频源不提供独立音频流，**Then** yt-dlp 使用 `bestaudio/best` 回退格式，确保能获取音频。

3. **Given** 用户在"视频+音频"模式下下载，**When** 下载完成，**Then** 获取包含视频和音频的完整文件。

4. **Given** 用户切换为音频模式，**When** 下载列表中的文件扩展名从 .mp4 变为 .m4a/.mp3，**Then** 重复检测系统正确区分不同格式。

**Edge Cases**:

- 音频质量预设映射到 yt-dlp 音频格式选择器（如 "高"→`bestaudio`、"中"→`bestaudio[abr<=128]`）
- 仅音频模式下视频信息面板显示"仅音频"标识
- 无可用音频流时回退到最佳通用格式

## Requirements *(mandatory)*

### Functional Requirements

**智能重复检测**:

- FR-001: 系统必须基于**视频 ID** 作为重复检测的主键；**去重范围是全局的（跨订阅）** —— 同一视频在库中只有一条记录、一个文件，记录**归属于首次下载它的订阅**。
- FR-002: 系统必须对比**已下载记录中的画质**与**订阅当前画质**，识别画质升级场景；画质档次全序与判定规则见用户故事 1。（格式对比不在本次范围）
- FR-003: 系统必须**周期性地**（每 5 分钟）检查已完成记录的文件是否仍存在，并在 UI 中把缺失呈现为「文件缺失」。**检查路径不参与存在性判定** —— 存在性只由周期同步一条路径负责。
- FR-004: 重复检测与画质判定的结果必须在 UI 中呈现为「**已下载**」或「**可升级**」两种派生状态，另加「文件缺失」「已删除」两个**事实性标记**（不是独立状态）。
- FR-005: 文件名模板变化不能影响重复检测的准确性（去重基于视频 ID，天然满足）。
- FR-006: 用户手动触发「重新下载 / 升级」时，系统必须**复用同一条记录**（置回下载中、清空错误、更新画质与文件路径），不新建记录。
- FR-007: 重新下载成功后若新路径与旧路径不同，系统必须**回收旧文件**；**失败时不回收**。顺序为**先落库新路径、再回收旧文件**。

**失败自动重试**:

- FR-008: 系统必须对**网络类错误**与 **HTTP 5xx / 408 / 429** 自动重试。
- FR-009: 其余 **HTTP 4xx** 与**无状态码的终态失败**（格式不可用 / 私享 / 已删除 / 需登录 / URL 不合法）**不得**自动重试。完整判据见用户故事 2。
- FR-010: 重试间隔必须递增（30s → 60s → 120s），最多 3 次；**参数为硬编码常量，不提供设置项**。
- FR-011: 系统必须在下载记录中保留**重试次数**与**最近一次重试时间**；重试次数在**新一轮下载开始时归零**、**成功时保留**。
- FR-012: 用户手动取消的下载不得自动重试，且取消**立即中断**正在等待的退避。
- FR-013: 退避等待期间必须**保持占用并发名额**。
- FR-014: 重试进行中必须在记录上体现为 `retrying` 状态，并在 UI 中显示重试次数与下一次重试倒计时。
- FR-015: `yt-dlp` 可执行文件无法启动时（路径 / 权限问题）不得重试，必须写入明确的失败原因。

**下载速度限制**（⚠️ 本次范围外，原文保留）:

- FR-016: 系统必须通过 `--limit-rate` 参数将限速传递给 yt-dlp
- FR-017: 限速值以 KB/s 为单位，前端输入范围为 0-99999
- FR-018: 值为 0 或空表示无限制
- FR-019: 动态调整限速仅对新任务生效

**网络代理支持**（⚠️ 本次范围外，原文保留）:

- FR-020: 系统必须支持 HTTP、HTTPS、SOCKS5 代理协议
- FR-021: 系统必须支持带认证的代理
- FR-022: 代理 URL 必须在保存时进行格式校验
- FR-023: 未配置代理时 yt-dlp 不得传递 `--proxy` 参数

**音频下载支持**（⚠️ 本次范围外，原文保留）:

- FR-024: 系统必须提供"视频+音频"和"仅音频"两种下载模式
- FR-025: 仅音频模式必须支持指定首选音频格式（m4a、mp3、opus、aac）
- FR-026: 无独立音频流时必须回退到通用格式
- FR-027: 下载模式变更后重复检测必须正确识别格式差异

### Key Entities

**本次范围**:

- **下载记录（`download_records.json` 中的一条记录）**：在既有字段之外新增
  - `quality: string` —— **下载时使用的画质 preset 字符串**（如 `"1080p"`、`"best"`）；**空串表示未知**（旧记录），未知永不参与升级判定。
  - `retry_count: number` —— 重试次数；新一轮下载开始时归零，成功时保留。
  - `last_retry_at: string | null` —— 最近一次重试时间（ISO 8601）。
  - 说明：**不存**实际分辨率、**不存**文件扩展名（扩展名从 `file_path` 后缀派生）。存**请求的 preset** 而非实际分辨率，是为了避免「用户选 1080p 但源最高 720p → 永远误报可升级」。
- **画质档次**：`480p` / `720p` / `1080p` / `1440p` / `2160p` / `best`，全序为 `480p < 720p < 1080p < 1440p < 2160p < best`；其它取值（含空串）视为**未知**，不参与比较。

## Assumptions

**本次范围**:

1. `yt-dlp` 提供稳定的**平台视频 ID**（YouTube 为 11 位 Base64），并把它输出在 `--flat-playlist --dump-json` 的每一行里 —— 去重与画质判定都建立在这个 ID 上。
2. 下载记录持久化在 `download_records.json`。**注意：既有记录中并没有画质与格式字段** —— 本次新增 `quality` / `retry_count` / `last_retry_at`，且全部为可选（旧记录读取时取默认值，`quality` 为空表示未知）。
3. **失败重试的最大次数与间隔是硬编码常量，用户不可配置**（3 次 / 30·60·120 秒）。原先与之矛盾的 `RetryConfig` 实体已删除。
4. `yt-dlp` 会把自己重试若干次（下载、分片、提取各自有默认重试次数）后才失败；本特性是在其放弃之后的**更长周期补刀**，接受由此带来的请求量放大。
5. `yt-dlp` 的失败原因只出现在 **stderr** 的 `ERROR:` 行里；退出码**没有**错误类型语义（`0` 成功 / `1` 任意错误 / `2` 参数错误 / `101` 取消）。
6. 输出文件名模板为 `%(title)s.%(ext)s`，**不含订阅或画质判别符** —— 因此同一视频在库中只有一份文件，这也是「去重范围为全局」的物理前提。

**本次范围外（原文保留）**:

1. `yt-dlp` 原生支持 `--limit-rate`、`--proxy`、`-f bestaudio[ext=xxx]` 参数。
2. 代理配置为全局设置，不支持订阅级代理。
3. 音频下载文件扩展名由 `yt-dlp` 根据 `-o` 模板和格式选择器自动确定。
